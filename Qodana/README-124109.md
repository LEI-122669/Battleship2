# Qodana – Deteção de Dead Code (Ficha 3, Tarefa 2A)

## Cheiro escolhido

**Dead Code**, associado aos cheiros *Speculative Generality* e *Comments* do catálogo de Martin Fowler: código (classes, métodos, campos, atribuições, imports ou código comentado) que existe no projeto mas nunca é usado.

O livro *Object-Oriented Metrics in Practice* (Lanza & Marinescu) não define uma estratégia de deteção baseada em métricas para este cheiro. Por isso, a deteção feita aqui é uma aproximação com inspeções do IntelliJ/Qodana que funcionam por análise de uso, e não por limiares de métricas.

## Tabela de mapeamento (passo 4)

| Cheiro (Fowler) | Inspeção no IDE | ID da inspeção | Métrica / limiar | Limitações |
|---|---|---|---|---|
| *Dead Code* (Speculative Generality / Comments) | *Commented out code* | `CommentedOutCode` | Linhas de código comentado; `minLines` = 2 por omissão | Heurística; não distingue código morto de exemplos intencionais em comentários. Limiar absoluto, não relativo ao sistema. |
| | *Unused declaration* | `unused` | Sem métrica numérica (binária: usado / não usado) | Depende dos *entry points*; falsos positivos com reflexão, frameworks e testes. Não deteta código só usado por testes nem abstrações "para o futuro" com um único uso. |
| | *Unused assignment* | `UnusedAssignment` | Sem métrica (análise de fluxo de dados) | Só intraprocedimental; não deteta valores devolvidos que quem chama ignora. |
| | *Unused import* | `UNUSED_IMPORT` | Sem métrica | Cobre só imports; indicador fraco do cheiro. |

## Reflexão

O Qodana detetou 223 instâncias de Dead Code no projeto completo, a maioria declarações não usadas, e no pull request detetou corretamente o código morto introduzido de propósito, apontando o ficheiro e as linhas certas (3 problemas para 4 alterações introduzidas). Parte das ocorrências no projeto completo são provavelmente falsos positivos da inspeção `unused`, como métodos e classes chamados por reflexão, pelo servidor REST ou apenas pelos testes, que o Qodana não reconhece como pontos de entrada. O resultado é muito sensível ao limiar: com `any: 0` o projeto completo falha sempre, por isso o gate só é útil em modo pull request, onde conta apenas os problemas novos. Ao contrário das estratégias do livro, que combinam várias métricas com limiares relativos ao sistema, aqui cada inspeção é binária ou usa um limiar absoluto, e o gate só conta o total de problemas.
